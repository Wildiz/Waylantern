# Learning curriculum: Software Quality Assurance Analyst

Turn requirements and risks into a traceable software test strategy.

[Home](../README.md) / [Curricula](curricula.md) / [Software, interfaces and embedded systems](professions-software.md#roles-in-this-group)

**Target profile:** [Software Quality Assurance Analyst](professions-software.md#software-qa-analyst)

**Starting point:** Learn the stated foundations first

**Type:** Waylantern editorial learning recipe. Related official sources are listed separately below.

## Before you start

- Ability to use a small application
- Basic requirements and data concepts
- Clear written communication

**What you will produce:** A risk-based test plan with traceable scenarios and an evidence-based quality recommendation.

**Resource coverage:** 2 of 4 stages have no recorded resource gap. Read the marked gaps before planning your study.

Resource access labels refer to the material or software. Open a resource's details to check prerequisites, hardware, APIs and other running costs before using it.

## Your sequence

1. [Clarify a requirement](#stage-1)
2. [Design test coverage](#stage-2)
3. [Analyze defects and evidence](#stage-3)
4. [Deliver the quality assessment](#stage-4)

<a id="stage-1"></a>
## 1. Clarify a requirement

**Learn:**

- Acceptance criteria
- Ambiguity
- Concrete examples

**Study resources** — consult the sections needed for this task; the resources may teach complementary skills:

- [Open Practice Library](https://github.com/openpracticelibrary/openpracticelibrary) — intermediate in this topic; free access. [Details](area-design-product.md#resource-open-practice-library).

**Practise:** Write criteria for a fictional booking feature and record unanswered rule questions.

**Advance when:** Make each criterion observable and leave unresolved rules explicitly undecided.

After the checkpoint, [continue to stage 2](#stage-2).

<a id="stage-2"></a>
## 2. Design test coverage

**Learn:**

- Equivalence classes
- Boundary values
- State transitions

**Resource still needed:** No dedicated test-analysis syllabus is verified; formal test-design techniques require a suitable specialist reference.

**Practise:** Create cases spanning valid, invalid and boundary booking inputs and state changes.

**Advance when:** Map each case to a rule or risk and identify a deliberate exclusion.

After the checkpoint, [continue to stage 3](#stage-3).

<a id="stage-3"></a>
## 3. Analyze defects and evidence

**Learn:**

- Severity and priority
- Traceability
- Residual risk

**Study resources** — consult the sections needed for this task; the resources may teach complementary skills:

- [Cypress Real World App](https://github.com/cypress-io/cypress-realworld-app) — intermediate in this topic; free access. [Details](area-testing.md#resource-cypress-real-world-app).

**Practise:** Collect results from a permitted workflow and classify a defect by observed impact.

**Advance when:** Separate evidence from suspected causes and connect the defect to an acceptance criterion.

After the checkpoint, [continue to stage 4](#stage-4).

<a id="stage-4"></a>
## 4. Deliver the quality assessment

**Learn:**

- Coverage gaps
- Release recommendation
- Evidence summary

**Resource still needed:** A verified test-strategy and release-risk assessment guide is missing; this is an editorial practice assessment, not certification.

**Practise:** Deliver the plan, results and a qualified recommendation for the fictional feature.

**Advance when:** Trace each conclusion to evidence and identify untested behavior and unresolved risks.

## After this recipe

Study formal test-design techniques and the application domain further; a recommendation communicates evidence rather than authorizing release automatically.
