# Learning curriculum: Developer Relations Specialist

Create a runnable example, support a learner and communicate actionable product feedback.

[Home](../README.md) / [Curricula](curricula.md) / [Leadership, product and technology relationships](professions-leadership.md#roles-in-this-group)

**Target profile:** [Developer Relations Specialist](professions-leadership.md#developer-relations-specialist)

**Starting point:** Learn the stated foundations first

**Type:** Waylantern editorial learning recipe. Related official sources are listed separately below.

## Before you start

- Can build and debug a small programme using the technology to be explained.
- Can write a short explanation and collaborate through Git.

**What you will produce:** A tested developer tutorial, a small support log and a product-feedback report tied to observed friction.

**Resource coverage:** 3 of 4 stages have no recorded resource gap. Read the marked gaps before planning your study.

Resource access labels refer to the material or software. Open a resource's details to check prerequisites, hardware, APIs and other running costs before using it.

## Your sequence

1. [Understand the developer task](#stage-1)
2. [Build a reproducible example and tutorial](#stage-2)
3. [Practise useful community support](#stage-3)
4. [Turn learning friction into product feedback](#stage-4)

<a id="stage-1"></a>
## 1. Understand the developer task

**Learn:**

- Audience
- First successful action
- Setup friction

**Study resources** — consult the sections needed for this task; the resources may teach complementary skills:

- [Open Source Guides](https://opensource.guide/) — beginner in this topic; free access. [Details](area-software.md#resource-open-source-guides).

**Practise:** Choose one small open-source library or tool you have used. Describe the target learner, the task they want to perform and the minimum successful result.

**Advance when:** Your brief identifies what the learner already knows and the exact first result they should obtain.

After the checkpoint, [continue to stage 2](#stage-2).

<a id="stage-2"></a>
## 2. Build a reproducible example and tutorial

**Learn:**

- Minimal examples
- Installation instructions
- Expected output

**Study resources** — consult the sections needed for this task; the resources may teach complementary skills:

- [GitHub Skills: Introduction to GitHub](https://github.com/skills/introduction-to-github) — beginner in this topic; free access. [Details](area-software.md#resource-github-skills-introduction-to-github).

**Practise:** Create a small practice repository with a runnable example, pinned setup assumptions, sample input and expected output. Explain each non-obvious action and test from a clean starting state.

**Advance when:** Someone following the tutorial can reproduce its advertised result, and limitations or environment assumptions are visible.

After the checkpoint, [continue to stage 3](#stage-3).

<a id="stage-3"></a>
## 3. Practise useful community support

**Learn:**

- Question clarification
- Issue triage
- Respectful contribution

**Study resources** — consult the sections needed for this task; the resources may teach complementary skills:

- [First Timers Only](https://www.firsttimersonly.com/) — beginner in this topic; free access. [Details](area-software.md#resource-first-timers-only).
- [Open Source Guides](https://opensource.guide/) — beginner in this topic; free access. [Details](area-software.md#resource-open-source-guides).

**Practise:** Use a fictional support request or contribute within a project community rules. Ask clarifying questions, reproduce the issue when possible and separate a documentation problem from a product defect.

**Advance when:** Your support log shows a clear problem statement, reproduction result and an appropriate next action without promising authority you do not have.

After the checkpoint, [continue to stage 4](#stage-4).

<a id="stage-4"></a>
## 4. Turn learning friction into product feedback

**Learn:**

- Evidence synthesis
- Feedback prioritisation
- Developer education outcomes

**Resource still needed:** A verified developer-relations programme covering community strategy, programme measurement and organisational responsibilities is not yet catalogued.

**Practise:** Ask a willing developer to try the example, record where they become blocked and propose one documentation or product improvement. Distinguish tutorial completion from adoption or revenue.

**Advance when:** The capstone includes a tutorial, runnable example, support log and prioritised feedback item supported by a concrete observation.

## After this recipe

Repeat with a different audience and contribute a small documented improvement through the project normal review process.
