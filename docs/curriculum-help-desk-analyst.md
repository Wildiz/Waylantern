# Learning curriculum: Help Desk Analyst

Receive, classify and communicate a support request so that the next person can act on it.

[Home](../README.md) / [Curricula](curricula.md) / [Operations, platforms and IT support](professions-operations.md#roles-in-this-group)

**Target profile:** [Help Desk Analyst](professions-operations.md#help-desk-analyst)

**Starting point:** Start with the basics

**Type:** Waylantern editorial learning recipe. Related official sources are listed separately below.

## Before you start

- Use basic computer applications and communicate clearly.
- Practise with fictional users and tickets.

**What you will produce:** A small ticket queue with recorded priorities, clear updates and evidence-based closure or escalation.

**Resource coverage:** 2 of 4 stages have no recorded resource gap. Read the marked gaps before planning your study.

Resource access labels refer to the material or software. Open a resource's details to check prerequisites, hardware, APIs and other running costs before using it.

<a id="stage-1"></a>
## 1. Ask questions that narrow the request

**Learn:**

- User goal and impact
- Reproduction details

**Resource still needed:** No reviewed help-desk interviewing curriculum is catalogued; these are editorial communication exercises.

**Practise:** Write short intake conversations for an access problem, an unavailable application and an unclear request.

**Advance when:** Each conversation captures the user's goal and impact without asking them to send passwords.

After the checkpoint, [continue to stage 2](#stage-2).

<a id="stage-2"></a>
## 2. Record and prioritise work

**Learn:**

- Ticket categories
- Impact and urgency

**Study resources** — consult the sections needed for this task; the resources may teach complementary skills:

- [GLPI](https://github.com/glpi-project/glpi) — intermediate in this topic; free access. [Details](area-it-support.md#resource-glpi).

**Practise:** Create three fictional tickets in a test queue and state the assumptions behind their relative priorities.

**Advance when:** The queue order is explained by impact and urgency, not invented service-level commitments or personal preference.

After the checkpoint, [continue to stage 3](#stage-3).

<a id="stage-3"></a>
## 3. Communicate and escalate clearly

**Learn:**

- Status updates
- Ownership handoff

**Resource still needed:** An employer's escalation matrix, service levels and reviewed customer-support communications guide are missing.

**Practise:** Write a progress update and a technical escalation for the same ticket, using different detail for each audience.

**Advance when:** The update gives the next contact point and the escalation includes checks already done and evidence still needed.

After the checkpoint, [continue to stage 4](#stage-4).

<a id="stage-4"></a>
## 4. Capstone: manage a small ticket queue

**Learn:**

- Resolution confirmation
- Reopened cases and knowledge notes

**Study resources** — consult the sections needed for this task; the resources may teach complementary skills:

- [GLPI](https://github.com/glpi-project/glpi) — intermediate in this topic; free access. [Details](area-it-support.md#resource-glpi).

**Practise:** Work the three fictional requests through updates, one resolution and one justified escalation; reopen one case when verification fails.

**Advance when:** The ticket histories show continuous ownership and closure is supported by a user-facing check rather than an administrative status change.

## After this recipe

Learn the actual service catalogue, access-verification rules and escalation paths before handling real customer requests.
