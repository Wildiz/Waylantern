# Learning curriculum: Software Quality Assurance Tester

Execute careful checks and communicate reproducible software problems.

[Home](../README.md) / [Curricula](curricula.md) / [Software, interfaces and embedded systems](professions-software.md#roles-in-this-group)

**Target profile:** [Software Quality Assurance Tester](professions-software.md#software-qa-tester)

**Starting point:** Start with the basics

**Type:** Waylantern editorial learning recipe. Related official sources are listed separately below.

## Before you start

- Basic computer and browser skills
- Permission to test the selected demo

**What you will produce:** A manual test cycle with defect reports and traceable retest evidence.

**Resource coverage:** 2 of 4 stages have no recorded resource gap. Read the marked gaps before planning your study.

Resource access labels refer to the material or software. Open a resource's details to check prerequisites, hardware, APIs and other running costs before using it.

## Your sequence

1. [Observe intended behavior](#stage-1)
2. [Execute focused cases](#stage-2)
3. [Write a reproducible report](#stage-3)
4. [Deliver the test-and-retest cycle](#stage-4)

<a id="stage-1"></a>
## 1. Observe intended behavior

**Learn:**

- Expected outcomes
- Test environment
- Application states

**Study resources** — consult the sections needed for this task; the resources may teach complementary skills:

- [Cypress Real World App](https://github.com/cypress-io/cypress-realworld-app) — intermediate in this topic; free access. [Details](area-testing.md#resource-cypress-real-world-app).

**Practise:** Run or inspect a permitted demo and describe a normal user flow in a named environment.

**Advance when:** State the initial conditions, action and expected visible outcome.

After the checkpoint, [continue to stage 2](#stage-2).

<a id="stage-2"></a>
## 2. Execute focused cases

**Learn:**

- Step-by-step checks
- Boundary inputs
- Actual results

**Resource still needed:** No dedicated manual-testing course is verified; the demo is a practice target, not a complete testing method.

**Practise:** Execute normal, empty and malformed-input cases and record what actually happened.

**Advance when:** Mark cases passed, failed or blocked with evidence rather than counting blocked cases as passed.

After the checkpoint, [continue to stage 3](#stage-3).

<a id="stage-3"></a>
## 3. Write a reproducible report

**Learn:**

- Minimal reproduction
- Expected versus actual
- Evidence hygiene

**Study resources** — consult the sections needed for this task; the resources may teach complementary skills:

- [Open Source Guides](https://opensource.guide/) — beginner in this topic; free access. [Details](area-software.md#resource-open-source-guides).

**Practise:** Report one permitted-lab defect with build details, steps and sanitized supporting evidence.

**Advance when:** A second person reproduces the problem without receiving credentials or personal data.

After the checkpoint, [continue to stage 4](#stage-4).

<a id="stage-4"></a>
## 4. Deliver the test-and-retest cycle

**Learn:**

- Regression checks
- Retest status
- Run summary

**Resource still needed:** A verified manual regression and defect-lifecycle reference is absent; these editorial exercises require explicit evidence rather than claimed certification.

**Practise:** Repeat the cases on a changed demo version and record fixed, remaining and blocked outcomes.

**Advance when:** Trace each status to a specific run and clearly identify untested environments.

## After this recipe

Expand test-design skills before automating and use authorized targets; a demo test cycle is not a professional qualification.
